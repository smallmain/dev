# 测试

[English](test.md) | 简体中文

使用 Vitest 进行测试。

## 执行模型

- 测试开始前构建完整 npm 产物到 `dist/npm/dev`。
- CLI 和 Oxlint 插件测试必须使用构建产物，不直接导入被测源码。
- 子进程统一设置 `CI=1`，捕获退出码、信号、标准输出和标准错误。
- 单个端到端测试的默认超时时间为 300 秒，超时后终止子进程并标记失败。

## 端到端测试

CLI 命令与 Oxlint 插件均以端到端方式验证：

- 在临时目录中搭建真实项目夹具，通过真实命令与真实工具链（如 Oxlint、Stylelint、Git）运行被测逻辑。
- 不得对被测命令自身或其调用的工具链进行 mock 或打桩。
- 仅当依赖会产生不可控的外部副作用（如联网安装依赖）时，方可在该外部边界使用最小化替身，且替身不得改变被测命令的行为。

## 隔离与清理

- 每组端到端场景使用独立临时目录，不依赖开发仓库中的项目文件状态。
- Git 场景覆盖系统级配置并使用夹具目录作为 `HOME` / `USERPROFILE`，避免读取用户 Git 配置。
- 需要模拟已安装包时，将构建产物和仓库依赖链接到临时项目，保持真实的模块解析关系。
- 测试成功后删除临时目录；测试失败或设置 `KEEP_TEST_TEMP=1` 时保留目录并输出路径。

## 覆盖范围

### CLI

- `create`：覆盖默认与自定义选项、非法选项、模板渲染、模板文件后缀、JSON 规范化、生成文件、脚本、依赖和包管理器调用。
- `create` 安装恢复：在未指定 `--yes` 的交互终端中覆盖可重试安装失败后拒绝和接受重试、重复失败，以及重试成功后不重新渲染项目并继续最终检查；覆盖指定 `--yes`、非交互执行、被中断和命令启动失败时立即失败。
- `create` 阶段控制：验证安装失败会阻止最终检查和成功报告，并验证安装成功后最终检查失败会阻止成功报告。
- `create` 成功场景必须将构建产物和真实检查工具作为已安装项目依赖提供，故意渲染至少一个不符合规范的文件，证明最终修复阶段会将其修复，并验证生成项目可立即通过 `sm check`。不得为了让该测试通过而预先格式化模板。
- `check`：分别覆盖 Oxlint、Stylelint、Oxfmt 的成功、失败和修复，文件类型筛选、子命令参数、退出码，以及提交信息的文本、文件和默认 Git 路径输入。
- `check` 工具选择：覆盖直接声明并已安装的工具分别使用显式配置和默认配置运行；跳过未声明的传递依赖工具，包括因其它包的 peer dependency 而安装的工具；跳过未安装工具；以及不运行已禁用工具类别。
- `staged-run`：使用下述四层测试验证其 CLI、Git 事务、恢复和 Hook 行为。
- `set-git-hook`：覆盖 Hook 内容、无 `.git` 时跳过、默认覆盖已有 Hook，以及清除 `core.hooksPath`。

#### staged-run

使用四个相互补充的测试层级：

1. 纯单元测试覆盖任务及管理参数解析、NUL 分隔 Git 记录解析、复制与重命名目标路径、Git 版本解析、事务状态转换、退出码与信号映射，以及参数列表递归拆分。单元测试可以注入内部适配器，但必须使用已构建的 CLI 模块而非源码模块。
2. 临时仓库端到端测试通过已构建的 `sm` 可执行文件和真实 Git 命令运行。覆盖已暂存新增、复制、修改、重命名，排除删除和特殊条目，pathspec 默认值与 magic，从子目录调用，传递绝对子进程路径，解析项目本地可执行文件，原始参数不经 Shell 解释而直接传递，由调用方提供子命令参数分隔符，包含空白及控制字符的文件名，无匹配时静默，以及参数分块串行执行。
3. 真实提交集成测试安装生成的 Hook，并通过默认 `git commit`、`git commit -- <path>` 和 `git commit -a` 执行。验证 npm 与 pnpm Hook 内容、提交成功、提交中止、候选暂存区与默认暂存区同步，以及无关暂存条目得到保留。
4. 故障注入测试在每个会修改状态的事务边界制造失败：持久备份、清单转换、隐藏部分修改、子进程启动与结束、活动暂存区重新暂存、父进程暂存区锁重新暂存、普通 patch 恢复、临时暂存区三方恢复、验证、回滚和清理。另在持久备份后终止真实子进程，以验证崩溃恢复。

仓库场景还必须覆盖：

- 完全及部分暂存的文本和二进制文件，包括匹配与未匹配的部分暂存文件。验证隐藏的未暂存修改得到恢复、仅匹配修复被暂存、成功的未匹配修改保持未暂存，以及未跟踪或忽略文件不受影响。
- 子进程失败、信号中断、启动失败、后续分块失败、子进程直接修改暂存区、patch 冲突、内部 Git 失败、回滚失败、指定及未指定 `--allow-empty` 的空结果，以及提交点后的清理失败。
- unborn 分支、linked worktree，以及已解决的 merge、cherry-pick、revert、rebase 和 am 状态。在可行时逐字节验证操作元数据，并验证 merge 空结果同时考虑两个父提交。
- 旧 Git 版本、裸仓库、未合并条目、intent-to-add 条目、sparse-checkout、sparse index 和 skip-worktree 条目在预检阶段被拒绝且不产生修改。
- worktree 级锁、活动锁与孤立锁、未完成事务阻止普通执行、列出恢复记录、可撤销恢复、消费已恢复记录、`cleanup-only`、强制丢弃，以及拒绝丢弃活动事务。
- 在提供相应信号的平台验证 `SIGINT` 与 `SIGTERM` 回滚及不可捕获终止后的持久恢复；其它平台仍须通过故障注入验证共用恢复语义。
- 输出契约：无匹配执行保持静默；成功执行不在子进程输出之外添加包装输出；事务或恢复诊断仅在失败时出现。

每个成功、回滚和恢复场景都必须检查相关的原始暂存区内容及 tree、暂存 diff、已跟踪工作树内容及 mode、未暂存 diff、操作元数据、未跟踪文件、事务资产和私有 ref，并验证 `refs/stash` 未改变。不得只依赖命令输出或 `git status` 摘要。

测试套件必须保持可移植，并可在支持的平台本地运行。新增 CI 工作流和设置性能阈值不属于本提案范围。

### 配置与插件

- 验证发布产物中的通用 Oxlint 配置可加载其 JavaScript 插件，并能执行插件规则。
- `comments`：覆盖缺少描述、存在描述、忽略 ESLint 指令和 `ignore` 选项。
- `consistent-esm-default-name`：覆盖模块解析与回退命名、默认再导出、忽略设置、模板转换、默认导出检查、默认导入与默认导出的安全自动修复、名称冲突和解析缓存失效。

## 断言

- 成功场景必须检查退出码为 `0` 且未超时。
- 失败场景必须检查非零退出码，并尽可能检查能标识失败原因的结构化诊断或可观察最终状态。
- 将退出码、信号、超时状态和可观察最终状态作为主要的机器可读契约，不得通过人类可读的摘要判断成功或失败。
- 工具提供 JSON、SARIF、报告文件或编程接口等结构化输出时，必须启用并解析该输出。应检查规则标识、文件路径、严重级别、数量和状态等语义字段，不得将完整标准输出或标准错误作为文本搜索。
- 不得通过移除 ANSI 控制序列，或规范化终端间距、颜色及摘要文案来使语义断言通过。第三方工具仅展示层面的变化不得导致测试失败。
- 仅当人类可读的标准输出或标准错误属于本包有意支持的接口时，才可检查其中的文本，例如帮助、用法或稳定的 CLI 错误。第三方输出可作为失败上下文，但不得作为唯一的语义断言。
- 工具不提供结构化输出时，应结合进程状态与可观察最终状态，或范围明确且由本包拥有的输出契约进行判断。
- 涉及文件、配置、Git 暂存区或自动修复的场景必须检查最终状态，不得只检查命令输出。
